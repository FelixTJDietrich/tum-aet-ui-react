# Accessibility

The components follow the WAI-ARIA Authoring Practices: correct roles, accessible names, states, keyboard operation and focus handling. This page lists what you get and what stays your job.

## What the components do

- Keyboard operation for every interactive part: arrow keys in listboxes, menus, tabs, radio groups and calendars, `Escape` closes popups, `Enter` and `Space` activate.
- Focus stays inside a modal dialog and returns to the trigger when it closes. Popups return focus to their trigger.
- Visible focus rings (`:focus-visible`) with a colour that has enough contrast in both themes.
- Messages use `role="alert"` for errors and `role="status"` otherwise. Table result counts and paginator summaries are announced.
- Animations respect `prefers-reduced-motion`.
- Each component is checked with axe-core in the automated tests, and the Storybook a11y addon checks every story. Colour contrast was checked in a real browser in both themes.

## What you have to do

- Give every control an accessible name: a visible label (use `FormField`) or an `aria-label`. Icon-only buttons always need one.
- Put one meaningful heading structure and landmarks on your pages; the components do not add them.
- Keep contrast when you override tokens (4.5:1 for text, 3:1 for interface parts).
- Do not rely on colour alone to show state. Components add icons or text for severities; keep that when you wrap them.
- Test with a keyboard and a screen reader. Automated checks find only part of the problems.

## Known limits

- Right-to-left layouts and touch input have not been verified yet.
- The tooltip is not shown on touch-only devices; do not put essential information in it.
